A resposta correta é **d) Nenhuma das opções ✅**, porque os atributos dos símbolos não terminais **podem ser sintetizados ou herdados**. Não são obrigatoriamente só de um tipo. Isto está diretamente no PDF de Análise Semântica. 

Mas para perceberes porquê, precisamos de encaixar isto no compilador.

## 1. O que é a análise semântica?

Já vimos que o compilador passa por diferentes análises:

| Fase                  | Pergunta que faz                                                      |
| --------------------- | --------------------------------------------------------------------- |
| **Análise léxica**    | “Estas sequências de caracteres formam tokens válidos?”               |
| **Análise sintática** | “Estes tokens estão organizados de acordo com a gramática?”           |
| **Análise semântica** | “Aquilo que está escrito faz sentido segundo as regras da linguagem?” |

O PDF apresenta exatamente estas três fases e diz que a análise semântica é a última fase da análise. 

Por exemplo:

```c
int x;
x = "ola";
```

### Análise léxica

Reconhece coisas como:

```text
int      → palavra-chave
x        → identificador
=        → atribuição
"ola"    → string
;        → ponto e vírgula
```

Tudo válido. ✅

### Análise sintática

A estrutura também pode ser válida:

```text
identificador = expressão ;
```

Portanto:

```c
x = "ola";
```

tem uma forma sintaticamente aceitável. ✅

### Análise semântica

Agora o compilador sabe:

```text
x é int
"ola" é string
```

e pergunta:

> Posso guardar uma string numa variável declarada como `int`?

Não.

Logo:

```text
ERRO SEMÂNTICO ❌
```

Este é precisamente o exemplo usado no PDF. 

Portanto:

> **Sintaxe = a estrutura está correta?**
> **Semântica = essa estrutura faz sentido?**

---

# 2. O que verifica a análise semântica?

Segundo o PDF, verifica, entre outras coisas, se:

* as variáveis foram declaradas;
* uma variável não foi declarada de formas incompatíveis;
* os tipos são compatíveis;
* identificadores e palavras reservadas estão a ser utilizados corretamente.

Por exemplo:

```c
int x;
x = 10;
```

✅ semanticamente correto.

Mas:

```c
int x;
x = 2.5;
```

pode ser incompatível dependendo das regras da linguagem.

E:

```c
x = 10;
```

sem nunca ter declarado `x`, também pode ser erro semântico. 

---

# 3. Onde entram as gramáticas?

Na análise sintática tínhamos uma gramática, por exemplo:

```text
Expr → Expr + Term
Expr → Term
Term → número
```

A gramática permite reconhecer:

```text
3 + 5
```

Mas há uma limitação:

A gramática consegue dizer:

> “Isto tem a estrutura de uma expressão.”

Mas **não sabe por si só que o resultado é 8**, nem sabe necessariamente os tipos dos elementos.

É aí que aparecem os **atributos** e as **ações semânticas**.

O PDF diz que a análise semântica estende as gramáticas usadas pela análise sintática. Essas extensões chamam-se **definições dirigidas pela sintaxe** e são constituídas por:

**atributos + ações/regras semânticas.** 

---

# 4. O que é um atributo?

Um **atributo é uma informação associada a um símbolo da gramática**.

Já conhecemos símbolos como:

```text
Expr
Term
número
id
```

Agora podemos guardar informação sobre eles.

Por exemplo:

```text
Expr.val
Expr.type
id.name
id.type
```

Significa:

```text
.val   → valor
.type  → tipo
.name  → nome
```

O PDF dá precisamente como exemplos de atributos:

```text
tipo
valor
nome
endereço
```



Portanto, se temos:

```text
3 + 5
```

podemos ter:

```text
3.val = 3
5.val = 5
Expr.val = 8
```

O `val` é um **atributo**.

---


































































Claro. A distinção fica muito mais clara se virmos **onde aparecem os atributos na árvore sintática**.

Vamos usar:

```c
contador = 742 + 5;
```

## 1. Primeiro, o analisador léxico

Ele reconhece os lexemas e produz tokens:

```text
LEXEMA       TOKEN
contador     ID
=            ATRIBUIÇÃO
742          NUM
+            SOMA
5            NUM
;            PONTO_VÍRGULA
```

Mas um token pode trazer também **informação adicional**.

Por exemplo:

```text
ID  → name = "contador"

NUM → val = 742

NUM → val = 5
```

Aqui `name` e `val` são **atributos**.

Ou seja, o token não diz apenas:

> “encontrei um número”

Pode também dizer:

> “encontrei um número e o valor desse número é 742”.

O PDF diz precisamente que os atributos são informações associadas a símbolos terminais e não terminais.

---

# 2. O que é então um atributo de um TERMINAL?

Os terminais são os símbolos que vêm efetivamente da entrada, como:

```text
ID
NUM
+
=
;
```

Por exemplo, neste código:

```c
742 + 5
```

temos dois tokens `NUM`.

Mas não queremos perder a informação de que um corresponde a `742` e o outro a `5`.

Então:

```text
primeiro NUM:
    val = 742

segundo NUM:
    val = 5
```

Visualmente:

```text
NUM
 │
 └── val = 742
```

e:

```text
NUM
 │
 └── val = 5
```

Portanto:

> **O atributo de um terminal dá informação sobre aquele token concreto.**

Outro exemplo:

```c
contador
```

O token é:

```text
ID
```

mas o atributo pode ser:

```text
ID.name = "contador"
```

Assim, o compilador sabe não só:

> “isto é um identificador”

mas também:

> “o identificador chama-se contador”.

---

# 3. Agora entra o NÃO TERMINAL

Suponhamos que a gramática tem:

```text
Expr → NUM + NUM
```

Aqui:

* `NUM` e `+` são **terminais**;
* `Expr` é **não terminal**.

`Expr` não veio diretamente do código.

Tu não escreveste:

```c
Expr
```

Escreveste:

```c
742 + 5
```

É a gramática que diz:

> “NUM + NUM forma uma Expr.”

Portanto a árvore fica aproximadamente:

```text
             Expr
           /   |   \
        NUM    +    NUM
        742          5
```

---

# 4. E qual é o atributo do não terminal `Expr`?

Agora podemos calcular informação sobre **a expressão inteira**.

Sabemos:

```text
NUM da esquerda:
val = 742

NUM da direita:
val = 5
```

Então podemos calcular:

```text
Expr.val = 742 + 5
         = 747
```

E também podemos guardar:

```text
Expr.type = integer
```

A árvore passa conceptualmente a ter esta informação:

```text
                 Expr
            val = 747
            type = integer
              /    |    \
             /     |     \
        NUM        +      NUM
      val=742            val=5
```

Agora vê a diferença:

### Terminais

Guardam informação sobre **elementos concretos da entrada**:

```text
NUM.val = 742
NUM.val = 5
ID.name = "contador"
```

### Não terminais

Guardam informação sobre **estruturas inteiras construídas pela gramática**:

```text
Expr.val = 747
Expr.type = integer
```

---

# 5. Outro exemplo com tipos

Considera:

```c
3 + 5
```

Os terminais podem trazer:

```text
NUM.val = 3
NUM.type = integer

NUM.val = 5
NUM.type = integer
```

A gramática reconhece:

```text
Expr → NUM + NUM
```

Então o não terminal `Expr` pode receber:

```text
Expr.val = 8
Expr.type = integer
```

Porque a expressão inteira:

```c
3 + 5
```

tem:

* valor `8`;
* tipo `integer`.

Portanto **`Expr.val` não é o valor da palavra "Expr"**.

`Expr` representa **a expressão inteira `3 + 5`**.

É como dizer:

```text
Expr
↓
representa 3 + 5
↓
val = 8
type = integer
```

---

# 6. Agora com uma atribuição completa

Considera:

```c
contador = 3 + 5;
```

Uma gramática poderia ter:

```text
Assign → ID = Expr ;
Expr   → NUM + NUM
```

A árvore seria aproximadamente:

```text
                Assign
              /   |   \    \
            ID    =   Expr   ;
                    / | \
                  NUM + NUM
```

E poderíamos ter atributos:

```text
ID.name = "contador"

primeiro NUM.val = 3
segundo NUM.val = 5

Expr.val = 8
Expr.type = integer
```

Depois a análise semântica pode perguntar:

> Qual é o tipo da variável `"contador"`?

Se a tabela de símbolos disser:

```text
contador → integer
```

então pode verificar:

```text
tipo de contador = integer
tipo de Expr     = integer
```

Compatível ✅

Mas se tivéssemos:

```c
contador = 2.5;
```

e `contador` fosse `integer`, a análise semântica poderia detetar uma incompatibilidade de tipos, precisamente usando estes atributos. O PDF apresenta este tipo de verificação semântica.



































































---

# 7. O que é uma ação semântica?

Não confundas **atributo** com **ação semântica**.

O atributo é a **informação**:

```text
Expr.val
```

A ação semântica é o **cálculo ou verificação que fazemos com essa informação**.

Por exemplo:

```text
Expr → Expr1 + Term
```

podemos acrescentar:

```text
Expr.val = Expr1.val + Term.val
```

Isto é uma **ação semântica**.

Se:

```text
Expr1.val = 3
Term.val = 5
```

então:

```text
Expr.val = 3 + 5
         = 8
```

O PDF resume muito bem:

> **Atributos = informação**
> **Ações = verificar, calcular, detetar erros.** 

---

# 8. Agora finalmente: atributo sintetizado

**Sintetizado significa que a informação sobe na árvore.**

Ou seja:

> o atributo do **pai é calculado a partir dos atributos dos filhos**.

Considera:

```text
Expr → Expr1 + Term
```

Na árvore:

```text
             Expr
           /   |   \
       Expr1   +   Term
```

Suponhamos:

```text
Expr1.val = 3
Term.val  = 5
```

Então calculamos:

```text
Expr.val = Expr1.val + Term.val
         = 8
```

Visualmente:

```text
             Expr.val = 8
                  ↑
             /         \
Expr1.val = 3         Term.val = 5
```

A informação está a ir:

> **dos filhos → para o pai**

Isto chama-se **atributo sintetizado**.

O PDF usa precisamente `3 + 5` para exemplificar isto. 

Portanto memoriza:

> **SINTETIZADO = sobe.
> Filhos → pai.**

---

# 9. Agora atributo herdado

Aqui a informação faz outro caminho.

Um atributo **herdado** recebe informação do contexto, por exemplo:

> do pai para o filho
> ou de um símbolo à esquerda para outro símbolo.

O exemplo do PDF é excelente.

Temos:

```c
int n1, n2, n3;
```

A gramática pode ter:

```text
D → T L
```

onde:

```text
T
```

representa o tipo:

```text
int
```

e:

```text
L
```

representa a lista:

```text
n1, n2, n3
```

Primeiro descobrimos:

```text
T.type = integer
```

Mas agora precisamos de dizer à lista `L`:

> Todos estes identificadores são `integer`.

Então fazemos:

```text
L.type = T.type
```

Logo:

```text
T.type = integer
        ↓
L.type = integer
```

A informação foi **passada para `L`**.

`L` não calculou o seu tipo a partir dos seus filhos. Recebeu-o do contexto.

Por isso:

```text
L.type
```

é um **atributo herdado**. 

Pensa:

```text
int n1, n2, n3
↑
o "int" tem de ser passado aos nomes
```

---


























































Sim — **os atributos herdados podem receber informação de duas formas principais** no modelo apresentado no PDF:

1. **Do pai para o filho**
2. **De um irmão à esquerda para outro irmão à direita**

O PDF diz precisamente que um atributo é herdado quando há dependências entre atributos de símbolos do lado direito da regra, ou quando um símbolo do lado direito depende do não terminal do lado esquerdo, isto é, do pai. 

Exemplo pai → filho:

```text
A → B
```

Se:

```text
B.tipo = A.tipo
```

então `B.tipo` é herdado, porque `B` recebe informação de `A`.

Exemplo irmão da esquerda → irmão da direita:

```text
D → T L
```

Aqui `T` e `L` são filhos de `D`.

Se:

```text
L.type = T.type
```

então `L.type` é herdado, porque `L` recebe informação do seu irmão à esquerda, `T`. É exatamente o exemplo do PDF para declarações como `int n1, n2, n3`. 

Portanto, a ideia correta é:

> **Sintetizado:** informação sobe dos filhos para o pai.
> **Herdado:** informação chega ao símbolo a partir do contexto — normalmente do pai ou de um irmão à esquerda.

E numa gramática **L-attributed**, os atributos herdados só podem depender do **pai ou de símbolos que estejam à esquerda**. 














































# 10. Diferença fundamental

Esta é a parte que deves guardar:

```text
SINTETIZADO

          PAI
           ↑
        informação
       /           \
    FILHO         FILHO

filhos → pai
```

Exemplo:

```text
3 + 5
↓
Expr.val = 8
```

Enquanto:

```text
HERDADO

          PAI
           ↓
        informação
           ↓
         FILHO

pai/contexto → filho
```

Exemplo:

```text
int n1, n2, n3
↓
"integer" é passado à lista de variáveis
```

---

# 11. Porque se chamam “sintetizado” e “herdado”?

**Sintetizar** significa formar algo a partir de outras informações.

Por exemplo:

```text
3 + 5
```

os filhos têm `3` e `5` e o pai **sintetiza**:

```text
8
```

Já **herdar** significa receber uma propriedade que vem de fora/de cima.

Por exemplo:

```text
int n1, n2
```

`n1` e `n2` **herdam o tipo `int`** indicado anteriormente.

---

# 12. Existem outros tipos além de sintetizado e herdado?

**No PDF, os atributos são tratados nestas duas categorias:**

* **sintetizados**
* **herdados**

Não é apresentado um terceiro tipo de atributo. 

Mas aparecem dois nomes relacionados:

```text
S-attributed
L-attributed
```

**Estes não são novos tipos de atributos. São tipos de gramáticas com atributos.**

Uma gramática **S-attributed** usa apenas atributos sintetizados.

Ou seja:

```text
S-attributed
→ apenas informação filhos → pai
```

Uma gramática **L-attributed** permite atributos herdados, desde que esses atributos dependam apenas do pai ou de símbolos que aparecem à esquerda. 

Portanto não confundas:

```text
TIPOS DE ATRIBUTOS:
sintetizado
herdado

CLASSIFICAÇÃO DA GRAMÁTICA:
S-attributed
L-attributed
```

# 13. Agora a pergunta do exame

> **Numa definição dirigida pela sintaxe, no âmbito da análise semântica, os atributos dos símbolos não terminais são:**

### a) São somente sintetizados ❌

Não. Podem ser sintetizados **ou herdados**.

### b) Não podem ser herdados ❌

Falso. O PDF explica explicitamente atributos herdados.

### c) São somente herdados ❌

Também falso. Podem ser sintetizados.

### d) Nenhuma das opções ✅

Correta, porque nenhuma das três afirmações anteriores descreve corretamente os atributos.

## Resposta

**✅ d) Nenhuma das opções.**

Justificação curta para o exame:

> **Os atributos associados aos símbolos não terminais podem ser sintetizados ou herdados. Os sintetizados dependem dos atributos dos filhos da árvore de parse; os herdados recebem informação do pai ou de outros símbolos do contexto.**
