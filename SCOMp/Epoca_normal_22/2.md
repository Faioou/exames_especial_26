Portanto, o ponto essencial é:

```text
DISCO / TECLADO / REDE

```

Mas:

```text

programa → CPU           ✅ diretamente
```

 o que é uma **tabela de interrupções**?

Imagine que acontecem várias situações diferentes:

```text
teclado precisa de atenção
disco terminou uma operação
divisão por zero
page fault
system call
...
```

Quando uma destas situações ocorre, a CPU precisa de saber:

> «Que código devo executar para tratar este acontecimento?»

É para isso que existe a **Interrupt Vector Table**, ou tabela de vetores de interrupção/exceção.

O PDF diz que essa tabela **associa cada pedido de interrupção a um handler** e que cada entrada contém o endereço desse handler. 

Um **handler** é simplesmente:

> o código preparado pelo sistema operativo para tratar aquele tipo de evento.

Imagine uma tabela muito simples:

| Número | Evento           | Handler                           |
| ------ | ---------------- | --------------------------------- |
| 0      | divisão por zero | código que trata divisão por zero |
| 1      | outro evento     | código que trata esse evento      |
| 2      | outro evento     | código que trata esse evento      |
| ...    | ...              | ...                               |

É exatamente a ideia representada no slide 8 do PDF: cada evento tem um número `k`, esse número serve de índice na tabela, e a entrada correspondente aponta para o **handler k**. 

Podemos representar assim:

```text
Aconteceu exceção n.º 2
          ↓
CPU consulta a tabela
          ↓
┌───────────────┐
│ 0 → handler 0 │
│ 1 → handler 1 │
│ 2 → handler 2 │ ← encontrou
│ 3 → handler 3 │
└───────────────┘
          ↓
CPU executa handler 2
```

Portanto, quando a pergunta diz:

> **«acesso às tabelas de interrupção»**

«aceder» significa aqui **consultar/manipular essa estrutura privilegiada que contém os endereços dos handlers**.

Por exemplo, imagine que um programa normal pudesse alterar livremente esta tabela. Poderia fazer isto:

```text
Antes:

interrupção do teclado
       ↓
handler legítimo do SO


Programa malicioso altera a tabela:


interrupção do teclado
       ↓
código do programa malicioso
```

Isso seria um enorme problema de segurança. É por isso que estas estruturas pertencem ao domínio privilegiado do sistema operativo.

Os próprios PDFs dizem que **durante a inicialização do SO é o kernel que fornece/configura os handlers** que a CPU utilizará quando ocorrerem exceções. 

Há ainda uma coisa importante na expressão:

> **alteração entre kernel e user mode**

Um programa normal também não pode simplesmente decidir:

```text
"Agora quero ser kernel."
```

Se pudesse, toda a proteção desaparecia.

A passagem para kernel mode tem de acontecer através de mecanismos controlados, por exemplo uma exceção/system call. O PDF explica que, quando ocorre uma exceção, a CPU pode mudar o nível de proteção de **user mode para kernel mode**. 

A ideia completa é:

```text
Programa normal
   USER MODE
       │
       │ trap / exceção / interrupção
       ↓
CPU faz mudança controlada
       ↓
   KERNEL MODE
       │
       │ executa handler
       ↓
regressa ao programa
   USER MODE
```

Por isso, para memorizar esta pergunta:

> **User mode pode fazer operações normais:** somas, leituras permitidas de memória, executar uma trap para pedir um serviço.

> **Kernel mode pode fazer operações privilegiadas:** controlar a mudança de privilégio e lidar com estruturas críticas como a tabela de interrupções.

E a frase-chave sobre a tabela é:

> **Tabela de interrupções = tabela que diz à CPU qual handler deve executar para cada tipo de interrupção/exceção.** 


































































Exatamente: **a trap acontece quando um programa em `user mode` faz uma system call ao kernel**. E é precisamente por isso que a opção **d) não pode ser correta**.

A pergunta diz:

> “O conjunto seguinte de instruções pode apenas ser executado em kernel mode”

Ou seja, **todas as operações da opção têm de ser exclusivas de kernel mode**.

Na opção d):

> **Operações de Trap (interrupção de software), alteração entre kernel e user mode.**

O problema está na primeira parte: **a trap é iniciada em user mode**, não apenas em kernel mode.

Os seus PDFs dizem:

> “System calls [are] invoked via a special instruction (a ‘trap’)”
> e essa exceção “transfers execution from user mode to kernel mode”. 

Portanto, a sequência é:

```text
Programa está em USER MODE
        ↓
executa a instrução TRAP / syscall
        ↓
ocorre a exceção
        ↓
CPU muda para KERNEL MODE
        ↓
kernel executa o serviço pedido
```

Veja o exemplo do próprio PDF:

```text
USER CODE                 KERNEL CODE

syscall
   │
   └────── TRAP ───────→  Open file
                           │
                           │
          ←────────────────┘
             regressa
```



Ou seja, a `trap` funciona como a **porta de entrada controlada do user mode para o kernel mode**.
