Sim. O ponto aqui é que a pergunta pressupõe que já conhece várias palavras técnicas. Vou começar **antes das interrupções**, para perceber de onde tudo vem, e só no fim voltamos às quatro opções.

## 1. O que está a acontecer dentro de um computador?

Imagine, de forma muito simplificada:

```text
Programa
   ↓
  CPU
   ↓
executa instruções
```

A **CPU (processador)** executa as instruções de um programa uma após outra.

Por exemplo, um programa pode ter instruções equivalentes a:

```text
somar
comparar
guardar um valor
ler um ficheiro
somar novamente
...
```

O PDF chama à sequência de instruções que a CPU está a executar **control flow**, ou **fluxo de controlo**. 

Portanto:

**fluxo de controlo = sequência normal de instruções que a CPU está a executar.**

---

# 2. O que é o Sistema Operativo?

O **Sistema Operativo (SO)** é, por exemplo:

* Windows
* Linux
* macOS

O SO é o software que gere os recursos do computador: CPU, memória, disco, teclado, rede, processos, etc.

Mas existe uma parte especialmente importante do SO chamada **kernel**.

Pense assim:

```text
SISTEMA OPERATIVO
┌───────────────────────┐
│ programas e serviços  │
│                       │
│      KERNEL           │ ← parte central e privilegiada
│                       │
└───────────────────────┘
```

O **kernel** tem permissões que os programas normais não têm.

Por exemplo, um programa normal não deve poder simplesmente dizer:

> "Vou controlar diretamente o disco como me apetecer."

Isso seria perigoso.

Então, quando um programa precisa de algo que só o SO pode fazer, **pede ao kernel**.

E é aqui que aparece um dos termos da pergunta.

# 3. O que é uma «chamada ao sistema operativo»?

Em inglês chama-se **system call**.

Uma **chamada ao sistema** é simplesmente:

> **um pedido feito por um programa ao kernel para que o sistema operativo execute um serviço por ele.**

Por exemplo, imagine um programa que quer abrir:

```text
notas.txt
```

O programa precisa de pedir ao SO:

```text
Programa:
"SO, abre-me o ficheiro notas.txt."
```

Isto é uma **system call**.

Os PDFs dizem exatamente que as *system calls* são o mecanismo através do qual os programas pedem serviços ao kernel. 

Exemplos típicos são:

```text
abrir ficheiro
ler ficheiro
escrever ficheiro
criar processo
...
```

O PDF mostra precisamente o exemplo de `open()` para abrir um ficheiro. 

Guarde então:

```text
PROGRAMA
   │
   │ "Preciso que faças isto por mim"
   ↓
SISTEMA OPERATIVO
```

Isto é uma **chamada ao sistema**.

---

# 4. O que é um periférico?

Um **periférico** é um dispositivo de hardware que comunica com o computador.

Por exemplo:

```text
teclado
rato
disco/SSD
placa de rede
impressora
...
```

Na matéria, os PDFs dão precisamente exemplos como:

* disco;
* placa de rede;
* teclado. 

Agora aparece um problema.

Imagine que o sistema operativo pediu ao disco:

> "Lê estes dados."

O disco pode demorar algum tempo.

O que deve a CPU fazer?

Não faz sentido ficar constantemente a perguntar:

```text
CPU: Já acabaste?
Disco: Não.

CPU: Já acabaste?
Disco: Não.

CPU: Já acabaste?
Disco: Não.

CPU: Já acabaste?
Disco: Sim.
```

Isso desperdiçaria tempo da CPU.

É precisamente para resolver situações destas que entram as **interrupções**.

---

# 5. O que é uma interrupção?

Este é o conceito central do exercício.

Uma **interrupção** é uma forma de algum componente avisar a CPU/SO:

> **"Aconteceu alguma coisa que precisa da tua atenção."**

Imagine que a CPU está tranquilamente a executar um programa:

```text
instrução 1
instrução 2
instrução 3
instrução 4
instrução 5
```

De repente, o disco termina uma operação:

```text
             DISCO
               │
               │ "ACABEI!"
               ↓
CPU ← INTERRUPÇÃO
```

A CPU interrompe temporariamente aquilo que estava a fazer e deixa o SO tratar esse acontecimento.

Depois pode continuar o programa.

O PDF diz que as exceções assíncronas — as interrupções — podem ocorrer independentemente da instrução que a CPU está naquele momento a executar. Quando ocorrem, a CPU pausa a tarefa atual e passa o controlo para um **interrupt handler**. 

Portanto, não pense em «interrupção» como:

> "o computador avariou."

Não.

Pense primeiro em:

> **interrupção = aviso que faz a CPU desviar temporariamente a sua atenção para tratar um evento.**

---

# 6. O que significa «sinalizar a ocorrência de um evento»?

Esta expressão da pergunta parece complicada:

> «os periféricos sinalizem a ocorrência de eventos»

Mas significa simplesmente:

> **os periféricos avisarem que aconteceu alguma coisa.**

**Sinalizar = avisar/notificar.**

**Evento = alguma coisa que aconteceu.**

Por exemplo:

```text
Carreguei numa tecla
        ↓
aconteceu um evento

Chegou um pacote pela rede
        ↓
aconteceu um evento

O disco terminou de ler dados
        ↓
aconteceu um evento
```

O periférico pode gerar uma interrupção para dizer:

> "CPU/SO, aconteceu este evento."

O próprio PDF dá como exemplos de interrupções de I/O:

* Ctrl+C no teclado;
* chegada de um pacote da rede;
* chegada de dados do disco. 

Assim:

```text
EVENTO
   ↓
periférico gera uma INTERRUPÇÃO
   ↓
CPU é avisada
   ↓
SO trata o evento
```

# 7. O que significa I/O?

Na opção **b)** aparece:

> «operação de leitura ou escrita no disco»

I/O significa:

**Input/Output = Entrada/Saída**

Em português também se usa **E/S**.

No caso de um disco:

```text
LEITURA:
Disco ─────→ computador
      dados

ESCRITA:
Computador ─────→ disco
           dados
```

Por exemplo, abre um ficheiro com uma fotografia:

```text
foto.jpg no SSD
      ↓
   leitura
      ↓
dados chegam ao computador
```

Uma operação de disco pode ser lenta relativamente à CPU. O PDF explica que, numa operação longa de I/O, o SO inicia a operação e pode deixar outro processo utilizar a CPU. Quando a operação finalmente termina, **o hardware gera uma interrupção para notificar o SO**. 

Isto é muito importante para o exercício.

# 8. Um exemplo completo

Imagine que está a utilizar um programa e ele quer ler um ficheiro.

Primeiro:

```text
PROGRAMA
   │
   │ "Quero ler ficheiro.txt"
   ↓
SISTEMA OPERATIVO
```

O programa faz um pedido ao SO.

Depois:

```text
SISTEMA OPERATIVO
        │
        │ manda iniciar a leitura
        ↓
       DISCO
```

A leitura demora.

Enquanto isso, a CPU pode fazer outra coisa.

Finalmente:

```text
DISCO terminou a leitura
        │
        │ INTERRUPÇÃO
        ↓
       CPU
        ↓
Sistema Operativo
```

O PDF mostra exatamente esta sequência para operações longas de I/O. 

É por isso que as interrupções são tão úteis: **a CPU não precisa de estar parada à espera do disco.**

# 9. Então o que é um «interrupt handler»?

Quando chega uma interrupção, alguém tem de tratar o assunto.

Esse código chama-se:

**interrupt handler = tratador/manipulador da interrupção**

Por exemplo:

```text
DISCO:
"Terminei!"

        ↓ interrupção

CPU
        ↓

Interrupt handler do disco:
"Ok. Vou verificar o que aconteceu."
```

O PDF explica que, numa operação de I/O, o *interrupt handler* pode identificar o dispositivo que gerou a interrupção, recolher o resultado da operação e atualizar o estado do processo que estava à espera. 

Não precisa de decorar isto já. Basta perceber:

> **handler = código executado para tratar determinado evento.**

# 10. Agora uma distinção muito importante: «exceção» e «interrupção»

Aqui é onde a matéria fica confusa porque aparecem vários nomes.

O PDF usa **ECF — Exceptional Control Flow** como conceito geral.

Isto significa:

> alguma coisa faz a CPU abandonar temporariamente a sequência normal de execução para tratar uma situação especial.

O PDF diz que isto serve, entre outras coisas, para:

```text
erros
periféricos
interrupções do temporizador
system calls
```



Dentro deste grande grupo temos diferentes tipos:

| Situação                                                   | Nome usado nos PDFs |
| ---------------------------------------------------------- | ------------------- |
| Um dispositivo externo chama a atenção da CPU              | **Interrupt**       |
| O programa pede intencionalmente um serviço ao SO          | **Trap**            |
| Uma instrução causa um problema potencialmente recuperável | **Fault**           |
| Ocorre um erro grave                                       | **Abort**           |

O próprio resumo do PDF diz que as exceções podem ser externas (**interrupts**) ou internas (**traps, faults e aborts**). 

Isto vai esclarecer a confusão da opção **a)**.

---

# 11. O que é uma trap?

Uma **trap** é provocada intencionalmente pelo programa.

Por exemplo:

```text
Programa:
"Quero que o SO abra este ficheiro."
```

O programa provoca uma entrada controlada no kernel.

O PDF diz:

> uma *trap* é uma exceção intencional gerada por software;

e dá **system calls** como exemplo. 

Portanto, em terminologia rigorosa:

```text
Programa → SO
       SYSTEM CALL
          ↓
         TRAP
```

Enquanto:

```text
Periférico → SO
       INTERRUPÇÃO
```

Esta é talvez **a distinção mais importante para decorar**.

---

# 12. O que é uma fault?

**Fault** significa aproximadamente uma falha detetada durante a execução de uma instrução.

Não é feita de propósito.

Por exemplo:

```text
programa tenta aceder a memória
                ↓
há um problema
                ↓
FAULT
```

O PDF diz que uma *fault* é uma exceção síncrona **não intencional** e que pode representar um erro potencialmente recuperável. 

Não precisa disso para escolher a resposta deste exercício, mas ajuda a compreender a opção **b)**.

---

# 13. O que é um abort?

Um **abort** corresponde a uma situação grave.

Por exemplo, o PDF apresenta:

> **fatal hardware error**

e mostra que o *abort handler* acaba por terminar o processo. 

Portanto, quando a opção **b)** diz:

> «nunca são utilizadas para sinalizar erros no hardware»

a palavra **nunca** já deve fazê-lo desconfiar.

A matéria também contém mecanismos para reagir a erros graves de hardware.

















Não exatamente. **Um `abort` pode resultar de um problema de hardware, mas “hardware” não significa necessariamente “periférico”.**

Pense primeiro nestes dois conceitos:

```text
HARDWARE
├── CPU / processador
├── memória
├── componentes internos
└── periféricos
     ├── disco
     ├── teclado
     ├── placa de rede
     └── etc.
```

Ou seja, **periféricos são hardware**, mas **nem todo o hardware é um periférico**.

Nos seus PDFs, o exemplo de `abort` é um **Machine Check**:

```text
Machine check → Abort
```



Isto significa que o próprio sistema de hardware/processador detetou um **erro fatal**. O slide seguinte representa precisamente:

```text
Fatal hardware error occurs
          ↓
       ABORT
          ↓
abort handler
          ↓
processo termina
```



Portanto, **não deve decorar `abort = erro de periférico`**.

A distinção que interessa é esta:

```text
PERIFÉRICO quer avisar que aconteceu algo normal
        ↓
   INTERRUPÇÃO

Exemplo:
disco terminou uma leitura
        ↓
   interrupção
```

Já:

```text
HARDWARE deteta um erro fatal
        ↓
       ABORT
```

Os próprios PDFs separam essas situações. Dizem que notificações de **disco, rede e timer** são eventos provenientes de dispositivos externos, enquanto o `abort` aparece associado a um **fatal hardware error**. 

Portanto:

**Interrupção** → normalmente é um **aviso externo**, muitas vezes de um periférico.

**Abort** → é uma **exceção interna grave**, causada por uma situação fatal, como um erro grave de hardware.

E há um detalhe muito importante no resumo do PDF: ele classifica as **interrupts como externas**, enquanto **traps, faults e aborts são internas**. 

Logo, para o exame, eu decoraria assim:

> **Periférico → interrupt**
> **Erro fatal de hardware → abort**

# 14. E o DMA?

A opção **d)** fala em:

> «DMA»

Procurei especificamente **DMA / Direct Memory Access nos PDFs que enviou e não encontrei uma explicação deste conceito**. Portanto, esta parte não vou fingir que vem dos PDFs.

Para conseguir interpretar a opção, deixo apenas o significado geral:

**DMA = Direct Memory Access = acesso direto à memória.**

É uma técnica que permite transferir dados entre um dispositivo e a memória sem obrigar a CPU a copiar individualmente todos esses dados.

Muito simplificadamente:

```text
SEM a ideia de DMA:

Dispositivo → CPU → memória


COM DMA:

Dispositivo ─────→ memória
              ↑
        transferência direta
```

Mas **esta explicação é conhecimento geral meu, não está sustentada nos PDFs que me forneceu**.

# 15. Agora já conseguimos «traduzir» a pergunta

A pergunta diz:

> **Num sistema computacional as interrupções...**

Em linguagem muito simples está a perguntar:

> **Para que servem as interrupções num computador?**

Agora leia cada resposta assim.

| Opção  | Tradução para linguagem simples                                                                                   |
| ------ | ----------------------------------------------------------------------------------------------------------------- |
| **a)** | Servem para permitir a entrada no SO e para os dispositivos avisarem que aconteceram eventos.                     |
| **b)** | Os dispositivos podem avisar que aconteceram coisas, mas interrupções nunca estão associadas a erros de hardware. |
| **c)** | Os dispositivos fazem chamadas ao sistema operativo.                                                              |
| **d)** | As interrupções servem **exclusivamente** para DMA.                                                               |

Agora já conseguimos eliminar respostas.

### c) está errada

Porque está a inverter os papéis.

**Quem faz uma system call é um programa**, não um periférico. 

```text
PROGRAMA → system call → SO        ✅

PERIFÉRICO → system call → SO      ❌
```

Um periférico normalmente notifica o sistema através de uma **interrupção**:

```text
PERIFÉRICO → interrupção → SO      ✅
```

### d) está errada

A palavra **«exclusivamente»** significa:

> só servem para isso e para absolutamente mais nada.

Mas os PDFs dão vários outros usos: teclado, rede, disco, temporizador, etc. 

Logo, não podem ser usadas **exclusivamente** para DMA.

### b) está errada

Outra vez aparece uma palavra absoluta:

> **«nunca»**

Os PDFs mostram que o mecanismo geral de exceções também trata situações de erro, incluindo erros graves de hardware.
