A resposta correta é **d)**.

Primeiro precisa de perceber apenas **4 ideias**: processo, pipe, `read`, `write` e “bloquear”.

### 1. O que é um pipe?

Um **pipe** é como um **tubo com espaço para guardar dados temporariamente**, usado para um processo enviar dados a outro.

Imagine:

```text
PROCESSO A                         PROCESSO B
(produtor)                         (consumidor)

   write()                             read()
      ↓                                  ↑
      └──────→ [ PIPE: dados ] ──────────┘
```

O processo A coloca dados no pipe.
O processo B retira dados do pipe.

Portanto:

* `write()` = **colocar dados no pipe**
* `read()` = **retirar dados do pipe**

O PDF mostra precisamente um processo a usar `read()` para receber valores de um pipe. 

### 2. O pipe pode estar vazio ou cheio

O pipe tem capacidade limitada. Imagine um tubo que só consegue guardar 3 caixas:

```text
PIPE VAZIO:

[   ][   ][   ]


PIPE COM DADOS:

[ A ][ B ][   ]


PIPE CHEIO:

[ A ][ B ][ C ]
```

Agora aparecem duas situações muito importantes.

Se o consumidor fizer:

```text
read()
```

mas o pipe estiver **vazio**, não há nada para ler.

Então o processo fica **bloqueado**, isto é:

> fica parado à espera até aparecer algum dado.

O PDF diz explicitamente:

> se um processo chama `read()` e não existem dados disponíveis, o **kernel bloqueia o processo até chegarem dados**. 

```text
PIPE VAZIO
    ↓
read()
    ↓
"NÃO HÁ NADA"
    ↓
processo espera
```

### 3. E se tentarmos escrever num pipe cheio?

Se o pipe já estiver cheio:

```text
[A][B][C] ← cheio
```

e outro processo fizer:

```text
write(D)
```

não há espaço para `D`.

Num pipe bloqueante normal, o escritor **fica à espera até existir espaço**:

```text
PIPE CHEIO
    ↓
write()
    ↓
"Não há espaço"
    ↓
processo espera
```

Esta é exatamente a mesma lógica do problema **produtor/consumidor** que aparece nos PDFs:

* produtor espera se não houver espaço;
* consumidor espera se não houver itens. 

---

## 4. O que significa produtor/consumidor?

Muito simples:

**Produtor = produz/coloca coisas.**

**Consumidor = retira/consome coisas.**

Num pipe:

```text
PRODUTOR             PIPE              CONSUMIDOR
                        	
 write()  ───────→ [ dados ] ───────→  read()
```

Logo:

```text
Produtor = quem faz write()
Consumidor = quem faz read()
```

E as regras são:

```text
PIPE VAZIO → consumidor/read espera

PIPE CHEIO → produtor/write espera
```

É por isso que a opção **d)** diz:

> “funcionamento semelhante ao algoritmo de sincronização do produtor/consumidor”

Exatamente.

## Agora as quatro respostas

**a) ❌ “Não permite implementar qualquer tipo de sincronização.”**

Falso. Acabámos de ver que o próprio bloqueio do pipe permite sincronizar processos.

Um pode ter de esperar pelo outro.

---

**b) ❌ Diz que é preciso chamar `read()` várias vezes para verificar se existem dados.**

Não.

Num pipe bloqueante:

```text
read()
  ↓
não há dados?
  ↓
fica à espera
```

Não precisa de estar constantemente:

```text
read()
read()
read()
read()
```

O PDF confirma que o kernel simplesmente bloqueia o processo até chegarem dados. 

---

**c) ❌ Leitores/escritores.**

Tem dois problemas.

Primeiro, diz:

> “`read` não apaga os dados lidos do pipe”

Isto está errado.

Quando faz `read()` num pipe, os dados lidos são **consumidos**, ou seja, retirados do pipe.

Exemplo:

```text
ANTES:
[A][B][C]

read() lê A

DEPOIS:
[B][C][ ]
```

Não fica:

```text
[A][B][C]   ❌
```

Segundo, isto não é o problema dos **leitores/escritores**. Nesse problema, vários leitores podem ler simultaneamente os mesmos dados, enquanto um escritor precisa de acesso exclusivo. Os PDFs descrevem precisamente essa diferença. 

---

**d) ✅ CORRETA**

> “`read` bloqueia se o pipe estiver vazio e `write` bloqueia se o pipe estiver cheio.”

Isto corresponde à lógica:

```text
              PIPE

PRODUTOR                  CONSUMIDOR
 write()                     read()
    ↓                          ↓

se CHEIO → espera       se VAZIO → espera
```

É a mesma ideia do **produtor/consumidor** dos PDFs: o produtor espera por espaço e o consumidor espera por um item. 

### Portanto, decore apenas isto

**Pipe = tubo onde um processo coloca dados e outro retira.**

**`write()` = coloca.**
**`read()` = retira.**
**Pipe vazio → `read()` espera.**
**Pipe cheio → `write()` espera.**

➡️ **Resposta: d)**.
