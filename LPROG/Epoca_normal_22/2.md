**O analisador sintático não cria a gramática — ele usa a gramática que já foi definida.**

# Distinção entre lexema, token e a relação com os símbolos das gramáticas



```text
LEXEMA
TOKEN
SÍMBOLO DA GRAMÁTICA
```

No contexto do analisador sintático, a relação correta é:

> **Os tokens correspondem aos símbolos terminais da gramática.**
> **Os lexemas são os textos concretos do programa que foram classificados nesses tokens.**
> **Os não terminais são categorias sintáticas criadas pela gramática**, como `ATRIBUIÇÃO`, `EXPRESSÃO`, `INSTRUÇÃO`, etc.

Usando o exemplo:

```text
x = 25;
```

O analisador léxico vê estes **lexemas**:

```text
x
=
25
;
```

Lexema significa simplesmente: **os caracteres concretos que apareceram no código**.

Depois classifica cada lexema num **token**:

```text
LEXEMA        TOKEN

x             IDENTIFICADOR
=             ATRIBUIÇÃO
25            NÚMERO
;             PONTO_E_VÍRGULA
```

Depois, o analisador sintático recebe essencialmente:

```text
IDENTIFICADOR ATRIBUIÇÃO NÚMERO PONTO_E_VÍRGULA
```

Agora entra a gramática. Por exemplo:

```text
INSTRUÇÃO -> IDENTIFICADOR ATRIBUIÇÃO NÚMERO PONTO_E_VÍRGULA
```

Aqui:

```text
INSTRUÇÃO
```

é **não terminal**.

Enquanto:

```text
IDENTIFICADOR
ATRIBUIÇÃO
NÚMERO
PONTO_E_VÍRGULA
```

são **terminais**.

Portanto:

```text
Código:
x = 25;

        ↓ análise léxica

Lexemas:
x      =      25      ;

        ↓ são classificados

Tokens:
IDENTIFICADOR  ATRIBUIÇÃO  NÚMERO  PONTO_E_VÍRGULA

        ↓ análise sintática

Gramática:
INSTRUÇÃO -> IDENTIFICADOR ATRIBUIÇÃO NÚMERO PONTO_E_VÍRGULA
↑                    ↑
não terminal         terminais
```

### Então onde entram os lexemas?

Os lexemas **não são “não terminais”**.

E, neste contexto, normalmente nem dizemos que o lexema é um símbolo da gramática sintática.

O lexema é o **exemplo concreto** que pertence a uma categoria/token.

Por exemplo:

```text
x
idade
contador
total
```

são quatro lexemas diferentes, mas todos podem ter o mesmo token:

```text
IDENTIFICADOR
```

Da mesma maneira:

```text
25
7
918
0
```

são lexemas diferentes, mas pertencem todos ao token:

```text
NÚMERO
```


É muito mais correto dizer:

> **tokens → terminais da gramática sintática**
> **não terminais → categorias estruturais da gramática**
> **lexemas → texto concreto do programa que originou os tokens**

Este ponto é mesmo fundamental para não baralhar análise léxica com análise sintática.

# O que é a gramática

Uma linguagem de programação tem regras que dizem quais construções são permitidas.

Por exemplo, poderíamos definir uma linguagem muito simples com esta regra:

```text
ATRIBUIÇÃO → IDENTIFICADOR = NÚMERO ;
```
**Isto é uma produção - uma regra da gramática**

Isto está a dizer:

> Uma atribuição válida é formada por um identificador, seguido de `=`, seguido de um número e terminado por `;`.

Esta regra faz parte da **gramática da linguagem**.

O teu PDF define precisamente uma gramática como um conjunto de regras segundo as quais são construídas as frases válidas da linguagem. 

Se receber:

```c
x = ;
```

os tokens seriam aproximadamente:

```text
IDENTIFICADOR   =   ;
```

Mas a gramática exigia:

```text
IDENTIFICADOR = NÚMERO ;
```

Está a faltar `NÚMERO`.

Então o analisador sintático conclui:

> ❌ Erro sintático.

Nos PDFs isto também aparece: a **análise sintática aplica regras gramaticais** e deteta sequências ilegais de tokens. 


### Vamos supor que a linguagem tem estas regras:

```text
INSTRUÇÃO → IDENTIFICADOR ATRIBUIÇÃO EXPRESSÃO PONTO_E_VÍRGULA

EXPRESSÃO → NÚMERO SOMA NÚMERO
```

Aqui temos os dois conceitos que estavam a causar confusão.

### Terminais

São:

```text
IDENTIFICADOR
ATRIBUIÇÃO
NÚMERO
SOMA
PONTO_E_VÍRGULA
```

Porquê?

Porque são os símbolos que podem ser **comparados diretamente com os tokens da entrada**.

Por exemplo:

```text
gramática espera: IDENTIFICADOR
entrada contém:   IDENTIFICADOR
```

Há correspondência.

O PDF chama aos terminais os símbolos pertencentes a `Σ`. 

---

### Não terminais

São:

```text
INSTRUÇÃO
EXPRESSÃO
```

Estes **não são tokens recebidos da análise léxica**.

O analisador léxico nunca envia:

```text
EXPRESSÃO
```

Ele envia coisas como:

```text
NÚMERO SOMA NÚMERO
```

`EXPRESSÃO` é uma categoria criada na **gramática** para dizer:

> uma determinada combinação de terminais e/ou outros não terminais forma uma expressão.

Por exemplo:

```text
EXPRESSÃO → NÚMERO SOMA NÚMERO
```

Portanto:

> **Terminal = pode ser confrontado diretamente com a entrada.**

> **Não terminal = representa uma estrutura definida por regras da gramática.**

O PDF chama aos não terminais **variáveis/símbolos não terminais**, pertencentes a `V`.

# PARSERS TOP-DOWN/LL VS BOTTOM-UP/LR

```text
TOP-DOWN  -> família/estratégia de análise de cima para baixo
LL        -> tipo importante de parser TOP-DOWN

BOTTOM-UP -> família/estratégia de análise de baixo para cima
LR        -> tipo importante de parser BOTTOM-UP
```

Os teus slides associam os parsers preditivos a LL(1) e os parsers SLR/LALR/LR ao processamento bottom-up por reduções.  

# TOP-DOWN

**Top-down** significa literalmente:

> começar pela estrutura mais geral da gramática e ir descendo até aos tokens da entrada.

O parser começa logicamente pelo **símbolo inicial da gramática**.

Imagina:

```text
INSTRUÇÃO
```

Esse é um não terminal.

O parser pergunta:

> "Como é que `INSTRUÇÃO` pode ser formada?"

Consulta a gramática:

```text
INSTRUÇÃO -> IDENTIFICADOR ATRIBUIÇÃO EXPRESSÃO ;
```

Agora já sabe que uma `INSTRUÇÃO` deve conter essas partes.

Depois encontra outro não terminal:

```text
EXPRESSÃO
```

e pergunta:

> "Como é formada uma EXPRESSÃO?"

Por exemplo:

```text
EXPRESSÃO -> NÚMERO SOMA NÚMERO
```

Substitui `EXPRESSÃO` por essa estrutura.

Portanto, a direção é:

```text
INSTRUÇÃO
      ↓
IDENTIFICADOR ATRIBUIÇÃO EXPRESSÃO ;
      ↓
IDENTIFICADOR ATRIBUIÇÃO NÚMERO SOMA NÚMERO ;
```

É isto que significa **top-down**:

```text
estrutura geral
      ↓
estruturas menores
      ↓
terminais/tokens
```

Não significa que o parser não recebe tokens. **Recebe os tokens normalmente.** A diferença está na forma como usa a gramática para os analisar.

---

# LL

**LL é uma família de parsers top-down.**

Portanto:

```text
LL ⊂ TOP-DOWN
```

---

# O que é LL(1) = Analisador Sintático Preditivo 

LL é um tipo de parser **top-down**.

* primeiro `L` = lê a entrada da esquerda para a direita
* segundo `L` = constrói uma derivação mais à esquerda
* `LL(1)` = faz isso olhando apenas **1 token à frente**

Exemplo de **LL(1)**:

```text
S -> aA | bB
```

Se o próximo token é `a`, escolhe:

```text
S -> aA
```

Se é `b`, escolhe:

```text
S -> bB
```

Portanto, com 1 token já sabe qual regra usar.

O problema aparece quando duas alternativas começam da mesma forma.

Exemplo:

```text
EXPRESSÃO -> NÚMERO SOMA NÚMERO
           | NÚMERO
```

O parser chega a `EXPRESSÃO` e olha 1 token à frente:

```text
NÚMERO
```

Mas as duas regras começam por `NÚMERO`:

```text
NÚMERO SOMA NÚMERO
NÚMERO
```

Então, só com esse 1 token, ele **não sabe qual escolher**.

É por isso que esta gramática, nesta forma, não é adequada para LL(1).

O mesmo acontece em:

```text
A -> 0A | 0A1 | 0
```

O próximo token é:

```text
0
```

mas as três regras começam por `0`.

Logo:

```text
LL(1) -> olha 1 token
```

e esse token não chega para decidir.

A ideia-chave é:

> **LL(1) funciona bem quando cada alternativa pode ser distinguida logo pelo primeiro token que vem a seguir.**



# Uma gramática recursiva à esquerda não é LL(1)



> **Se a gramática tem recursão à esquerda, podes excluir logo LL(1)** na forma em que está.

### Portanto:

Se vires algo como:

```text
A -> Aα
```

ou, por exemplo:

```text
S -> SS
S -> Sa
```

já sabes:

```text
não é LL(1)
```

## Atenção a um pormenor importante

Isto vale não só para **recursão à esquerda imediata**, como:

```text
A -> Aα
```

mas também para **recursão à esquerda indireta**, por exemplo:

```text
A -> Bx
B -> Ay | z
```

Porque no fundo:

```text
A => Bx => Ayx
```

ou seja, `A` acaba por voltar a começar por `A`.


---





































## APONTAMENTO — Quando uma gramática NÃO serve diretamente para um analisador preditivo e um Analisador sintático em descida recursiva.


### 1. Recursividade à esquerda direta

```text
A → Aa | b
```

`A` chama novamente `A` antes de consumir entrada.

```text
A ⇒ Aa ⇒ Aaa ⇒ ...
```

❌ Não LL(1).
❌ Descida recursiva direta entra em recursão infinita.

---

### 2. Recursividade à esquerda indireta

```text
A → Bx
B → Ay | z
```

Porque:

```text
A ⇒ Bx ⇒ Ayx
```

Voltámos a `A` à esquerda.

❌ Não LL(1).
❌ Problema também para descida recursiva direta.

---

### 3. Alternativas com o mesmo FIRST

```text
A → ab | ac
```

Ao ver apenas:

```text
a
```

o analisador LL(1) não sabe se deve escolher:

```text
ab
```

ou:

```text
ac
```

Logo:

```text
FIRST(ab) ∩ FIRST(ac) = {a}
```

❌ Não é LL(1).

Mas uma descida recursiva **com retrocesso** pode experimentar `ab` e, se falhar, voltar atrás e experimentar `ac`.

---

### 4. Conflito FIRST/FOLLOW com ε

```text
A → a | ε
```

Se:

```text
a ∈ FOLLOW(A)
```

quando o analisador vê `a`, pode ficar sem saber se escolhe:

```text
A → a
```

ou:

```text
A → ε
```

❌ Não LL(1).

---

### 5. Gramática ambígua

Uma gramática é ambígua quando **a mesma palavra pode ter duas árvores sintáticas diferentes**.

Exemplo típico:

```text
E → E+E | E*E | id
```

A palavra:

```text
id + id * id
```

pode ter mais de uma árvore.

❌ Uma gramática ambígua nunca é LL(1).

Mas atenção: isto **não significa que um programa de descida recursiva com retrocesso seja incapaz de reconhecer a palavra**; o problema é que a análise não é única.

---

### REGRA PARA DECORAR

Para **LL(1) / analisador preditivo**, verifica:

```text
Recursividade à esquerda?      → NÃO LL(1)
Ambiguidade?                   → NÃO LL(1)
FIRST/FIRST com interseção?    → NÃO LL(1)
FIRST/FOLLOW com conflito ε?   → NÃO LL(1)
```

Para **descida recursiva normal**, o grande problema direto é:

```text
recursividade à esquerda
```

Se nas tuas sebentas o professor usar **“descida recursiva” como “descida recursiva preditiva”**, então aplicam-se **exatamente os mesmos critérios de LL(1)**.

# BOTTOM-UP

Agora esquece momentaneamente LL.

**Bottom-up** trabalha no sentido contrário.

Em vez de começar pelo símbolo inicial:

```text
INSTRUÇÃO
```

começa pelos **tokens da entrada**.

Por exemplo:

```text
IDENTIFICADOR ATRIBUIÇÃO NÚMERO SOMA NÚMERO ;
```

E tenta descobrir:

> "Que estruturas maiores da gramática consigo reconhecer nestes símbolos?"

Vai juntando/reconhecendo estruturas até chegar ao símbolo inicial.

A direção é:

```text
tokens
   ↓
estruturas intermédias
   ↓
símbolo inicial
```

Ou seja:

```text
baixo
 ↓
cima
```

Daí **bottom-up**.

---

# REDUÇÃO

Para perceber bottom-up tens de perceber uma palavra: **redução**.

Suponhamos que a gramática contém:

```text
EXPRESSÃO -> NÚMERO SOMA NÚMERO
```

E o parser encontra:

```text
NÚMERO SOMA NÚMERO
```

Pode dizer:

> "Esta sequência corresponde ao lado direito da regra de `EXPRESSÃO`."

Então substitui:

```text
NÚMERO SOMA NÚMERO
```

por:

```text
EXPRESSÃO
```

Isto chama-se uma **redução**:

```text
NÚMERO SOMA NÚMERO
         ↓
     EXPRESSÃO
```

Repara que estamos a usar a regra ao contrário:

Gramática:

```text
EXPRESSÃO -> NÚMERO SOMA NÚMERO
```

Redução:

```text
NÚMERO SOMA NÚMERO -> EXPRESSÃO
```

Os teus PDFs dizem exatamente isto: nos parsers bottom-up, quando símbolos no topo da stack correspondem ao lado direito de uma regra, podem ser substituídos pelo símbolo do lado esquerdo; isso é uma **redução**. 

---

# LR

**LR é uma família de parsers bottom-up.**

Portanto:

```text
LR ⊂ BOTTOM-UP
```

Assim como LL é uma família importante de top-down, LR é uma família importante de bottom-up.

Existem variantes mencionadas nos teus PDFs:

```text
LR
SLR
LALR
```

Todas trabalham segundo esta lógica de **shift/redução** e usam uma stack. 

No nome `LR`:

```text
L = lê a entrada da esquerda para a direita

R = corresponde a uma derivação mais à direita,
    considerada em sentido inverso
```

Esta segunda parte é precisamente uma das razões pelas quais LR parece menos intuitivo no início: o parser está a **reduzir** a entrada em vez de gerar a palavra a partir do símbolo inicial.

---

# EXEMPLO DE LR / BOTTOM-UP

Usamos exatamente a mesma entrada:

```text
IDENTIFICADOR ATRIBUIÇÃO NÚMERO SOMA NÚMERO ;
```

e exatamente a mesma gramática:

```text
INSTRUÇÃO -> IDENTIFICADOR ATRIBUIÇÃO EXPRESSÃO ;

EXPRESSÃO -> NÚMERO SOMA NÚMERO
```

O parser reconhece:

```text
NÚMERO SOMA NÚMERO
```

e sabe que isso corresponde a:

```text
EXPRESSÃO -> NÚMERO SOMA NÚMERO
```

Então reduz:

```text
IDENTIFICADOR ATRIBUIÇÃO NÚMERO SOMA NÚMERO ;

                       ↓

IDENTIFICADOR ATRIBUIÇÃO EXPRESSÃO ;
```

Agora observa que toda esta sequência:

```text
IDENTIFICADOR ATRIBUIÇÃO EXPRESSÃO ;
```

corresponde ao lado direito de:

```text
INSTRUÇÃO -> IDENTIFICADOR ATRIBUIÇÃO EXPRESSÃO ;
```

Então reduz novamente:

```text
IDENTIFICADOR ATRIBUIÇÃO EXPRESSÃO ;

                    ↓

                INSTRUÇÃO
```

Chegámos ao símbolo inicial.

Logo a entrada é aceite.

A direção foi:

```text
IDENTIFICADOR ATRIBUIÇÃO NÚMERO SOMA NÚMERO ;
                       ↓
IDENTIFICADOR ATRIBUIÇÃO EXPRESSÃO ;
                       ↓
                  INSTRUÇÃO
```

Isto é **bottom-up**.

---

# SHIFT

Num parser LR real aparece também muito a palavra **shift**.

É mais simples do que parece.

O parser tem uma **stack**.

`shift` significa essencialmente:

> pegar no próximo token da entrada e colocá-lo na stack.

Por exemplo:

```text
entrada:
NÚMERO SOMA NÚMERO ...

stack:
[ ]
```

faz shift:

```text
stack:
[NÚMERO]

entrada:
SOMA NÚMERO ...
```

outro shift:

```text
stack:
[NÚMERO SOMA]

entrada:
NÚMERO ...
```

outro:

```text
stack:
[NÚMERO SOMA NÚMERO]
```

Agora reconhece que:

```text
NÚMERO SOMA NÚMERO
```

corresponde a uma regra e faz uma **redução**:

```text
[NÚMERO SOMA NÚMERO]
          ↓
[EXPRESSÃO]
```

Portanto:

```text
SHIFT   = colocar mais entrada na stack

REDUCE  = substituir uma sequência
          pelo não terminal correspondente
```

É por isso que se fala muitas vezes em **parsers shift-reduce** quando se fala de LR.

---

# LL VS LR

Agora fica muito mais simples comparar:

|                       | LL                              | LR                                                  |
| --------------------- | ------------------------------- | --------------------------------------------------- |
| Estratégia            | Top-down                        | Bottom-up                                           |
| Começa logicamente em | símbolo inicial                 | tokens da entrada                                   |
| Operação principal    | expandir não terminais          | reduzir sequências                                  |
| Direção conceptual    | `S -> tokens`                   | `tokens -> S`                                       |
| Usa a gramática       | no sentido normal das produções | reconhecendo o lado direito e reduzindo ao esquerdo |

A diferença que deves guardar é esta:

```text
LL / TOP-DOWN

INSTRUÇÃO
     ↓ expande
IDENTIFICADOR = EXPRESSÃO ;
     ↓ expande
IDENTIFICADOR = NÚMERO + NÚMERO ;
```

Enquanto:

```text
LR / BOTTOM-UP

IDENTIFICADOR = NÚMERO + NÚMERO ;
                  ↓ reduz
IDENTIFICADOR = EXPRESSÃO ;
                  ↓ reduz
              INSTRUÇÃO
```

**Ambos recebem exatamente os mesmos tokens do analisador léxico.** O PDF confirma que o scanner produz os tokens que serão usados pelo parser. 

A diferença é apenas **a estratégia usada pelo parser para demonstrar que essa sequência de tokens pertence à linguagem definida pela gramática**.

Se tiveres de guardar só duas frases, guarda estas:

> **TOP-DOWN / LL: começo no símbolo inicial e tento chegar aos tokens.**

> **BOTTOM-UP / LR: começo nos tokens e tento reduzi-los até ao símbolo inicial.**





































# Derivação


**Derivar** significa **aplicar as regras da gramática para ir transformando um símbolo noutros símbolos até chegar a uma palavra/frase formada só por terminais**.

A **derivação** é o **processo completo dessas transformações**.

No teu exercício:

```text
A → 0A | 0A1 | 0
```

o símbolo inicial é `A`.

Uma derivação possível é:

```text
A
⇒ 0A
⇒ 00A
⇒ 000
```

Aqui fizemos:

```text
A → 0A
```

depois outra vez:

```text
A → 0A
```

e finalmente:

```text
A → 0
```

Portanto, `000` foi **derivada** a partir de `A`.

A forma mais simples de guardar isto é:

> **Derivar = aplicar uma regra.**
> **Derivação = o caminho inteiro de aplicações de regras até chegar à palavra final.**

E é por isso que o PDF diz que o **símbolo inicial** é o símbolo “a partir do qual todas as frases são derivadas”. 











---































































# Símbolo inicial

> **O símbolo inicial é o não terminal a partir do qual somos obrigados a começar a aplicar as regras da gramática.**

O PDF diz precisamente que `S` representa o **“símbolo inicial a partir do qual todas as frases são derivadas”**. 

Imagina esta gramática:

```text
S → 0A
A → 1
```

Existem dois não terminais:

```text
S
A
```

Mas a gramática tem de dizer:

> “Qual deles uso primeiro?”

Se o **símbolo inicial for `S`**, então somos obrigados a começar assim:

```text
S
```

Depois usamos a regra:

```text
S → 0A
```

e obtemos:

```text
S ⇒ 0A
```

Depois:

```text
A → 1
```

e:

```text
S ⇒ 0A ⇒ 01
```

Portanto, o símbolo inicial é simplesmente o **ponto de partida**.

Agora repara numa coisa importante: **“S” em `G = (V, Σ, P, S)` é o nome que damos à posição “símbolo inicial” na definição geral. Não significa que o símbolo tenha obrigatoriamente de se chamar literalmente `S`.**

No teu exercício:

[
G=({A},{0,1},{A\rightarrow0A\mid0A1\mid0},A)
]

a estrutura geral é:

[
G=(V,\Sigma,P,S)
]

Então comparamos posição por posição:

```text
V = {A}
Σ = {0,1}
P = {A → 0A | 0A1 | 0}
S = A
```

Esse último:

```text
A
```

quer dizer:

> **O símbolo inicial desta gramática é A. Portanto, sempre que quisermos gerar uma palavra, começamos em A.**

Assim:

```text
A
↓
0A
↓
00A
↓
000
```

Nunca começamos diretamente em:

```text
0
```

nem em:

```text
1
```

porque `0` e `1` são terminais, não são o símbolo inicial.

Portanto, no teu exercício, guarda simplesmente:

> **Símbolo inicial = o não terminal onde começa a derivação.**

E aqui:

> **símbolo inicial = A.**

# 1. Para que serve uma gramática?

Estamos na parte de **análise sintática** de um compilador.

Recorda:

```text
programa
   ↓
análise léxica
   ↓
tokens
   ↓
ANÁLISE SINTÁTICA
   ↓
...
```

O analisador léxico reconhece os **tokens**.

Por exemplo, perante:

```c
x = 3 + 5;
```

poderia produzir algo semelhante a:

```text
IDENTIFICADOR   =
NÚMERO          +
NÚMERO          ;
```

Agora aparece outro problema:

> Como é que o compilador sabe se estes tokens estão numa **ordem permitida pela linguagem**?

É aí que entram as **gramáticas**.

O próprio PDF começa por dizer que uma gramática é usada para **descrever e analisar linguagens** e contém regras segundo as quais são construídas as frases válidas. 

Portanto:

**gramática = conjunto de regras que diz quais as estruturas/frases que uma linguagem permite.**

---

# 2. Um exemplo muito simples

Imagina que criamos uma linguagem extremamente pequena que só permite frases como:

```text
Pedro joga
Maria joga
```

Poderíamos definir:

```text
FRASE → NOME VERBO
NOME → Pedro | Maria
VERBO → joga
```

O símbolo `|` significa:

> **ou**

Portanto:

```text
NOME → Pedro | Maria
```

significa:

> NOME pode ser substituído por `Pedro` **ou** por `Maria`.

O PDF utiliza exatamente este tipo de notação e explica que `|` representa uma **alternativa**. 

---

# 3. O que significa a seta →?

Quando temos:

```text
NOME → Pedro
```

a seta significa aproximadamente:

> **NOME pode ser substituído por Pedro.**

Ou:

> **NOME produz Pedro.**

Estas regras chamam-se **produções**.

O PDF define uma produção genericamente como:

[
\alpha \rightarrow \beta
]

indicando que os símbolos do lado esquerdo podem ser substituídos pelos do lado direito. 


---



















# 5. Agora conseguimos perceber a definição formal de uma gramática `G = (V, Σ, P, S)`

O PDF diz que formalmente uma gramática é:

[
G=(V,\Sigma,P,S)
]

São **quatro coisas que definem completamente a gramática**. 

Vamos uma de cada vez.

### V — conjunto dos não terminais

Por exemplo:

```text
V = {A, B}
```

significa:

> nesta gramática existem dois símbolos não terminais: `A` e `B`.

---

### Σ — alfabeto / conjunto dos terminais

Esta letra é a letra grega **sigma**:

[
\Sigma
]

Por exemplo:

```text
Σ = {0,1}
```

significa:

> as frases finais desta linguagem são construídas utilizando `0` e `1`.

---

### P — produções

São as regras.

Por exemplo:

```text
A → 0A
A → 1
```

Estas regras dizem como podemos substituir `A`.

---

### S — símbolo inicial

Precisamos de saber:

> onde começa a derivação?

Esse símbolo chama-se **símbolo inicial**.

O PDF diz precisamente que `S` é o símbolo a partir do qual todas as frases são derivadas. 

Atenção: não significa que o símbolo inicial tenha obrigatoriamente de se chamar `S`.

Podemos ter:

```text
símbolo inicial = A
```

É exatamente isso que acontece no teu exercício.

---





Quer dizer **escrever a gramática G3 na sua forma formal completa**, isto é:

```text
G3 = (V, Σ, P, S0)
```

O PDF define formalmente uma gramática exatamente assim: `G = (V, Σ, P, S)`, em que `V` é o conjunto de não terminais, `Σ` é o alfabeto de terminais, `P` é o conjunto de produções e `S` é o símbolo inicial. 

No teu exercício, a gramática que obtivemos foi:

```text
S0 -> 0S0 | 1S1
S1 -> 1S3
S2 -> 0S1
S3 -> 0S3 | 1S2 | ε
```

Portanto, a **caracterização formal de G3** é:

```text
G3 = (V, Σ, P, S0)
```

onde:

### 1. V — conjunto dos não terminais

Como cada estado do autómato virou um não terminal:

```text
V = {S0, S1, S2, S3}
```

### 2. Σ — conjunto dos terminais

O enunciado diz que o alfabeto do autómato é:

```text
Σ = {0, 1}
```

Portanto estes são também os terminais da gramática.

### 3. P — conjunto das produções

```text
P = {
S0 -> 0S0 | 1S1;
S1 -> 1S3;
S2 -> 0S1;
S3 -> 0S3 | 1S2 | ε
}
```

### 4. Símbolo inicial

O estado inicial do autómato é `S0`, portanto o símbolo inicial da gramática também é:

```text
S0
```

Logo, tudo junto:

```text
G3 = ({S0, S1, S2, S3}, {0, 1}, P, S0)
```

onde:

```text
P = {
S0 -> 0S0 | 1S1;
S1 -> 1S3;
S2 -> 0S1;
S3 -> 0S3 | 1S2 | ε
}
```

Portanto, **“caracterizar formalmente” não é voltar a converter o autómato**. É pegar na gramática já obtida e dizer formalmente quais são os seus quatro componentes: `V`, `Σ`, `P` e o símbolo inicial.

# 10. O que significa então “linguagem gerada pela gramática”?

É simplesmente:

> **o conjunto de todas as palavras que conseguimos produzir começando no símbolo inicial e aplicando as regras.**

O PDF define isto como `L(G)` — a linguagem gerada por `G`. 

No nosso caso aparecem, por exemplo:

```text
0
00
000
001
0001
00011
...
```

Não precisamos ainda de determinar exatamente todas as palavras possíveis para resolver o exercício.

# 14. O que é uma gramática “ambígua”

Esta definição aparece diretamente no PDF.

O PDF diz:

> uma gramática é ambígua quando é possível obter **a mesma frase através de duas árvores de derivação distintas**. 

Traduzindo:

Se a gramática consegue construir exatamente a mesma palavra de **duas maneiras estruturalmente diferentes**, temos ambiguidade.

---

# 15. Vamos testar a nossa gramática

Temos:

```text

A → 0A1
A → 0
```

Vamos tentar produzir:

```text
0001
```

Primeira maneira:

```text
A
⇒ 0A
⇒ 00A1
⇒ 0001
```

Vê o que fizemos:

```text
A → 0A

depois:
A → 0A1

depois:
A → 0
```

Resultado:

```text
0001
```

# 16. Agora uma segunda maneira

Começamos outra vez em `A`:

```text
A
⇒ 0A1
⇒ 00A1
⇒ 0001
```

Agora fizemos:

A → 0A1

depois:
A → 0A

depois:

```

Outra vez!

# 17. Porque é que isto prova ambiguidade?

Porque as **árvores de derivação são diferentes**.

Na primeira, a raiz utiliza:

```text
A → 0A
```

e só o `A` seguinte utiliza:

```text
A → 0A1
```

Temos aproximadamente:

```text
        A
       / \
      0   A
         /|\
        0 A 1
          |
          0
```

As folhas, lidas da esquerda para a direita:

```text
0 0 0 1
```

---

Na segunda derivação, logo na raiz usamos:

```text
A → 0A1
```

e depois:

```text
A → 0A
```

Temos:

```text
        A
       /|\
      0 A 1
       / \
      0   A
          |
          0
```

As folhas também são:

```text
0 0 0 1
```

Portanto:

**mesma palavra: `0001`**

mas:

**duas árvores diferentes.**

Segundo a definição do próprio PDF:

> **gramática ambígua.** 

Isto é a peça principal para responder à pergunta.

# 18.O que é um parser?

`Parser` é simplesmente o termo inglês utilizado para:

> **analisador sintático.**

Ele recebe os tokens e tenta verificar se a sequência respeita as regras da gramática.

Por exemplo, se tivermos uma gramática:

```text
S → 0A
A → 1
```

e recebermos:

```text
01
```

o parser consegue verificar:

```text
S
↓
0A
↓
01
```

Logo a frase é válida.

# 6. Então existem LL(2), LL(3), etc.?

**Sim.**

De forma geral escrevemos:

```text
LL(k)
```

em que `k` é o número de tokens de avanço que podem ser necessários.

Assim:

```text
LL(1)
```

→ olha até **1 token** à frente.

```text
LL(2)
```

→ pode olhar até **2 tokens** à frente.

```text
LL(3)
```

→ pode olhar até **3 tokens** à frente.

E genericamente:

```text
LL(k)
```

→ olha até `k` tokens à frente.

O teu PDF fala especificamente de `LL(1)` e diz que o `(1)` representa o número de terminais de avanço necessários. 

A existência de `LL(2)`, `LL(3)`, `LL(k)` já é uma generalização da notação, não algo que esse slide desenvolva.




# Exemplos de LL(1) e LL(2)



## LL(1)

Considere esta gramática:

```text
S -> aA | bB
A -> c
B -> d
```

O parser está em `S` e tem de escolher entre:

```text
S -> aA
```

ou:

```text
S -> bB
```

Agora olha apenas para **1 símbolo/token à frente**.

Se a entrada começar por:

```text
a
```

já sabe imediatamente:

```text
S -> aA
```

Se começar por:

```text
b
```

já sabe imediatamente:

```text
S -> bB
```

Por exemplo, para a entrada:

```text
ac
```

o parser vê o primeiro símbolo:

```text
a
```

e pensa:

```text
Próximo símbolo = a

S -> aA   ✅ pode ser
S -> bB   ❌ não pode ser
```

Só precisou de olhar para **1 símbolo**.

Logo, neste exemplo:

```text
LL(1) ✅
```

---

# LL(2)

Agora considera:

```text
S -> abA | acB
A -> d
B -> e
```

O parser chega a `S` e tem duas possibilidades:

```text
S -> abA
```

ou:

```text
S -> acB
```

Agora imagina que o próximo símbolo da entrada é:

```text
a
```

O parser olha apenas para esse `a`.

Temos:

```text
S -> abA
     ↑
     começa por a
```

e:

```text
S -> acB
     ↑
     também começa por a
```

Então, com apenas **1 símbolo de lookahead**, não consegue decidir.

```text
próximo símbolo = a

S -> abA   ? pode ser
S -> acB   ? também pode ser
```

Portanto:

```text
LL(1) ❌
```

Mas agora deixamos o parser olhar para **2 símbolos**.

Se os dois próximos forem:

```text
ab
```

já sabe:

```text
S -> abA
```

Se forem:

```text
ac
```

já sabe:

```text
S -> acB
```

Por exemplo, entrada:

```text
abd
```

Com 1 lookahead:

```text
a
```

não chega:

```text
abA ?
acB ?
```

Com 2 lookaheads:

```text
ab
```

já decide:

```text
S -> abA ✅
```

Portanto este exemplo é:

```text
LL(2) ✅
LL(1) ❌
```

A ideia para decorar é:

> **LL(1): 1 token é suficiente para distinguir as alternativas.**

> **LL(2): 1 token não chega, mas olhando para os próximos 2 já consegue distinguir.**

E o `(1)` ou `(2)` **não significa quantos tokens a regra contém**. Significa quantos tokens o parser pode precisar de observar à frente para decidir **qual produção aplicar**.

# O SCANNER É UMA “SUBROTINA” DO PARSER?

Porque, numa implementação típica, o parser está a analisar a frase e vai pedindo ao scanner:

> “Dá-me o próximo token.”

Imagina:

```text
x = 25;
```

O parser pede:

```text
parser -> scanner:
"qual é o próximo token?"
```

Scanner lê `x` e responde:

```text
IDENTIFICADOR
```

O parser continua e volta a pedir:

```text
"próximo token?"
```

Scanner lê `=`:

```text
ATRIBUIÇÃO
```

Depois:

```text
NÚMERO
```

e depois:

```text
PONTO_E_VÍRGULA
```

Portanto podes imaginar:

```text
                  chama
PARSER --------------------------> SCANNER
  |                                  |
  |                                  | lê caracteres
  |                                  |
  | <--------------------------      |
  |        devolve TOKEN              |
  |
  | continua análise sintática
```

É neste sentido que a afirmação chama ao scanner uma **subrotina do parser**: o parser pode chamar o scanner sempre que precisa do próximo token.

A sequência geral fica:

```text
código fonte
    ↓
SCANNER / LEXER
análise léxica
    ↓
tokens
    ↓
PARSER
análise sintática
    ↓
estrutura / árvore
    ↓
SEMANTIC ANALYZER
análise semântica
