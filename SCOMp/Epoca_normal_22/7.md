# Semáforo de sincronização VS Semáforo Mutex

Imagine **dois processos reais**:

* **Processo A**
* **Processo B**

E um semáforo chamado `S`, que começa em:

```text
S = 0
```

O PDF diz que `down(S)` faz isto: se `S` for 0, o processo que chamou `down(S)` fica bloqueado; `up(S)` aumenta o valor do semáforo. 

Exemplo concreto:

```text
Processo A:
1. down(S)
2. imprimir "Olá"
```

```text
Processo B:
1. fazer um trabalho
2. up(S)
```

No início:

```text
S = 0
```

O **Processo A** chega primeiro a:

```text
down(S)
```

Como `S = 0`, o **Processo A fica parado ali**. Não executa ainda o `imprimir "Olá"`.

Depois o **Processo B** faz o seu trabalho e chega a:

```text
up(S)
```

Isso faz o semáforo deixar de estar a 0. O **Processo A**, que estava parado no `down(S)`, pode então continuar e executar:

```text
imprimir "Olá"
```

Portanto, quando eu dizia:

> “só continuas quando eu der autorização”

o significado correto e concreto era:

> **O Processo A fica bloqueado no `down(S)` enquanto `S=0`. O Processo B executa `up(S)`, e isso permite que o Processo A deixe de estar bloqueado.**

Não há nenhuma “autorização” humana. É só o valor do semáforo que controla se o processo fica parado ou continua.

Agora o **mutex** é diferente no objetivo.

Imagine que A e B querem alterar a mesma variável:

```text
saldo = 100
```

Temos:

```text
M = 1
```

O Processo A faz:

```text
down(M)
```

Como `M=1`, A entra e `M` passa para 0.

Enquanto A está a mexer no saldo, o Processo B tenta:

```text
down(M)
```

mas agora `M=0`, portanto B fica bloqueado.

Quando A acaba:

```text
up(M)
```

e B pode entrar.

Aqui o objetivo não é “A esperar que B termine uma tarefa anterior”. O objetivo é:

> **impedir que A e B mexam na mesma coisa ao mesmo tempo.**

O PDF resume exatamente assim: semáforo inicializado a **0** pode ser usado para notificar outro processo de que uma condição aconteceu; inicializado a **1** pode ser usado para **exclusão mútua**. 

Portanto, em português muito direto:

**Semáforo de sincronização (`S=0`)**
→ um processo fica parado até outro processo executar `up(S)`.

**Mutex (`M=1`)**
→ vários processos querem entrar na mesma zona, mas só **um de cada vez** pode entrar.

No seu exercício:

```text
S1 e S2
```

servem para fazer **um processo esperar por outro**.

```text
M
```

serve para impedir que **os dois P2 mexam em `rc` ao mesmo tempo**.











































































































# Exercicio 7

A ideia geral do exercício é: **há 3 processos que precisam de executar certas partes numa determinada ordem**, e os semáforos servem para os obrigar a esperar uns pelos outros.

## 1. Primeiro: o que são P1 e P2?

Na tabela aparecem dois tipos de código:

```text
P1                     P2
```

Mas o enunciado diz que vão existir **três processos**, pela ordem:

```text
P2, P1, P2
```

Portanto, pense assim:

```text
Processo A → executa o código P2
Processo B → executa o código P1
Processo C → executa o código P2
```

Ou seja, **há dois processos diferentes a executar o mesmo código P2**.

---

## 2. Então para que servem S1, S2 e M?

Embora os três sejam semáforos, estão a ser usados para objetivos diferentes.

### S1 e S2

Começam a:

```text
S1 = 0
S2 = 0
```

Portanto servem sobretudo para fazer processos **esperar por acontecimentos**.

Por exemplo:

```text
P1 faz down(S2)
```

Como S2 começa a 0:

```text
P1 fica parado
```

até alguém executar:

```text
up(S2)
```

---

### M

`M` começa a:

```text
M = 1
```

Aqui está a ser usado como um **mutex**.

Mutex significa:

> permitir que **apenas um processo de cada vez** mexa numa determinada coisa.

Neste caso, a coisa que queremos proteger é principalmente:

```text
rc
```

Os PDFs explicam que mutexes/semáforos são usados para impedir acesso concorrente descontrolado a dados partilhados. 

Imagine dois P2:

```text
P2-A
P2-B
```

Ambos querem alterar `rc`.

Com `M`:

```text
P2-A → down(M)
       M passa 1 → 0
       entra

P2-B → down(M)
       vê M = 0
       espera
```

Só depois de P2-A executar:

```text
up(M)
```

é que P2-B pode entrar.

---

## 3. O que é `rc`?

O enunciado diz:

```text
rc = 0
```

e que é uma **variável partilhada**.

Isso significa que os dois processos P2 veem **a mesma variável**.

Não temos:

```text
P2-A → rc próprio
P2-B → rc próprio
```

Temos:

```text
             rc
             ↑ ↑
            /   \
         P2-A   P2-B
```

Ambos alteram o mesmo `rc`.

---

## 4. O que significa `rc++`?

Muito simples:

```text
rc++
```

significa:

> aumentar `rc` em 1.

Se:

```text
rc = 0
```

depois de:

```text
rc++;
```

fica:

```text
rc = 1
```

Outro P2 faz:

```text
rc++;
```

fica:

```text
rc = 2
```

Portanto, aqui `rc` está a funcionar como um **contador** dos processos P2 que chegaram àquela parte do código.

---

## 5. O que significa `if (rc == 2)`?

`if` significa:

> **se**

Logo:

```text
if (rc == 2)
```

significa:

> **se rc for igual a 2...**

Por exemplo:

```text
rc = 1

if (rc == 2)
```

é falso → não faz a instrução.

Mas:

```text
rc = 2

if (rc == 2)
```

é verdadeiro → executa a instrução seguinte.

---

## 6. O que é a secção crítica?

Uma **secção crítica** é uma parte do programa cuja execução precisa de ser controlada relativamente aos outros processos, normalmente porque envolve um recurso/dado partilhado.

Os PDFs explicam que quando vários processos acedem sem controlo a dados partilhados podem surgir *race conditions*, e por isso usa-se sincronização. 

Aqui não é mostrado o que existe dentro da:

```text
Secção crítica
```

Só sabemos que é uma parte importante cuja ordem está a ser controlada.

---

## 7. Agora vamos ler o P1

P1 tem:

```text
1. down(S2);

2. Secção crítica

3. up(S1);
```

### Linha 1

```text
down(S2)
```

Mas inicialmente:

```text
S2 = 0
```

Portanto P1 chega aqui e:

```text
P1 → BLOQUEIA
```

Não pode entrar ainda na secção crítica.

Só poderá continuar quando algum P2 executar:

```text
up(S2)
```

---

### Linha 2

Quando finalmente for libertado:

```text
P1 entra na sua secção crítica
```

---

### Linha 3

Quando termina:

```text
up(S1)
```

Ou seja:

> P1 sinaliza: **“já terminei esta parte; alguém que esteja à espera em S1 pode avançar.”**

---

## 8. Agora o P2

Tem:

```text
1. down(M);
2. rc++;
3. if (rc == 2) up(S2);
4. up(M);

5. Secção crítica

6. down(M);
7. if (rc == 2) down(S1);
8. up(M);
```

Vamos linha a linha.

### Linha 1

```text
down(M)
```

Como inicialmente:

```text
M = 1
```

o primeiro P2 consegue entrar:

```text
M: 1 → 0
```

E nenhum outro P2 pode entrar nesta zona enquanto `M=0`.

---

### Linha 2

```text
rc++;
```

O primeiro P2 faz:

```text
rc: 0 → 1
```

---

### Linha 3

```text
if (rc == 2) up(S2);
```

Mas neste momento:

```text
rc = 1
```

Logo:

```text
1 == 2 ? NÃO
```

Não faz `up(S2)`.

Portanto P1 continua bloqueado.

---

### Linha 4

```text
up(M)
```

Liberta o mutex:

```text
M: 0 → 1
```

Agora outro P2 pode mexer em `rc`.

---

## 9. Quando chega o segundo P2

O segundo P2 faz:

```text
down(M)
```

M estava 1:

```text
M: 1 → 0
```

Depois:

```text
rc++;
```

Como já estava em 1:

```text
rc: 1 → 2
```

Agora:

```text
if (rc == 2)
```

é verdadeiro.

Então executa:

```text
up(S2)
```

E isto é importante porque P1 estava:

```text
down(S2)
   ↓
BLOQUEADO
```

Logo o segundo P2 está essencialmente a dizer:

> **“Já chegaram dois P2. P1 já pode avançar.”**

---

 10. Esta é a primeira grande sincronização

O esquema é:

```text
Primeiro P2 chega
      ↓
    rc = 1
      ↓
P1 ainda NÃO pode passar


Segundo P2 chega
      ↓
    rc = 2
      ↓
   up(S2)
      ↓
P1 pode passar
```

Portanto:

> **P1 só consegue chegar à sua secção crítica depois de rc chegar a 2.**

E `rc` só chega a 2 depois de **dois processos P2** terem executado `rc++`.

Essa é uma das ideias centrais do código.

---

## 10. E a segunda metade de P2?

Depois da secção crítica, P2 faz:

```text
6. down(M);
7. if (rc == 2) down(S1);
8. up(M);
```

Primeiro:

```text
down(M)
```

volta a proteger esta zona para que um P2 de cada vez faça o teste.

Depois:

```text
if (rc == 2)
    down(S1);
```

Se `rc == 2`, tenta fazer:

```text
down(S1)
```

Mas inicialmente:

```text
S1 = 0
```

Portanto pode ficar parado aqui:

```text
P2 → down(S1) → BLOQUEADO
```

Quem é que faz:

```text
up(S1)
```

?

**P1**, depois da sua secção crítica.

Logo temos outra relação:

```text
P2 espera em S1
        ↑
        │
P1 termina a sua secção crítica
        │
      up(S1)
```

Ou seja, **S1 serve para um P2 esperar que P1 termine**.

---

## 11. O desenho completo

A lógica geral é aproximadamente esta:

```text
P2-A             P1                P2-B

rc = 1
                  |
               down(S2)
               ESPERA
                  |
                                   rc = 2
                                   up(S2)
                                      |
                  ←-------------------+
                  |
             P1 DESBLOQUEIA
                  |
            secção crítica
                  |
               up(S1)
                  |
                  +------------→ liberta P2
```


---

## 13. Porque `M=1`, mas S1 e S2 começam em 0?

Porque queremos comportamentos diferentes.

### M = 1

Queremos que **o primeiro processo possa entrar imediatamente**:

```text
M = 1
down(M)
↓
entra
```

Depois fica 0 e impede o próximo.

Isto é típico de um mutex.

### S1 = 0 e S2 = 0

Queremos que qualquer processo que faça imediatamente:

```text
down(S1)
```

ou:

```text
down(S2)
```

**espere**.

Esses semáforos funcionam como portas inicialmente fechadas.

---

## 14. Porque proteger `rc++` com M?

Imagine que não existia M.

Os dois P2 podiam tentar fazer:

```text
rc++;
```

ao mesmo tempo.

Isso pode criar uma **race condition**.

Por exemplo, ambos leem:

```text
rc = 0
```

P2-A pensa:

```text
0 + 1 = 1
```

P2-B também pensa:

```text
0 + 1 = 1
```

e ambos escrevem 1.

Resultado:

```text
rc = 1
```

quando devia ser:

```text
rc = 2
```

É exatamente este tipo de problema que os mecanismos de sincronização procuram evitar. 

Com M:

```text
P2-A mexe em rc
↓
termina
↓
P2-B mexe em rc
```

Logo obtemos corretamente:

```text
0 → 1 → 2
```
